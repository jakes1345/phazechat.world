Security

How Phaze protects your messages, and where it doesn’t.

A plain description of Phaze’s end-to-end encryption, the parts of the app it doesn’t cover, and how to report a security problem. Everything here matches the open-source code.

Short version: one-to-one DMs are end-to-end encrypted once both apps have exchanged keys, and the server only ever sees ciphertext for them. Group chats, Spaces, stories, calls, attachment files and metadata are not end-to-end encrypted.

Encryption design

Direct messages use NaCl box: X25519 key agreement with XSalsa20-Poly1305 authenticated encryption. The web app uses tweetnacl-js and the Android app uses Lazysodium, a libsodium binding. Both produce the same wire format, so web and Android users can read each other’s messages.

  1. Keys are made on your device. Each install generates its own keypair the first time it runs. The web app keeps it in the browser’s local storage; Android keeps it in app-private storage.
  2. Public keys are exchanged, not stored. When you open a chat, your app sends a key request and your contact’s app answers with its public key. The server forwards these only between friends and never stores public keys.
  3. Every message is sealed separately. Each message gets a random 24-byte nonce. It travels as E2EE: followed by the hex-encoded nonce and ciphertext, and the server stores and relays that string as-is.
  4. Key changes are flagged. The web app pins a fingerprint of each contact’s key (the first 8 bytes of its SHA-256 hash) the first time it sees it. If the key later changes, it refuses the new key and shows a warning. The Android app doesn’t pin keys yet.

On the web, the message box shows a lock icon once encryption is active for a conversation.

Keys & backups

Because keys live on your device, a new phone or browser would normally mean a new identity, and older messages encrypted to the old key couldn’t be read there. Key backup solves this and is optional:

  • Your keypair is encrypted on your device with a key derived from a recovery PIN you choose (at least 8 characters), using PBKDF2-SHA256 with 600,000 iterations and AES-256-GCM. The PIN is the only thing protecting the backup from the server, so a long one matters.
  • Only the ciphertext, the salt and the iteration count are uploaded. The server never sees your PIN or your private key.
  • Restoring the backup on a new device keeps the same identity, so contacts using the web app don’t see a key-change warning.

A short PIN can be guessed by someone who has the backup ciphertext, so choose one that isn’t easy to guess.

What isn’t end-to-end encrypted

Everything below is encrypted in transit, but not end to end. Unless noted, the Phaze server (or the third party named) can read it:

  • DMs sent before keys are exchanged. If your app doesn’t have your contact’s key yet, both apps fall back to plain text. No lock icon means no end-to-end encryption.
  • Attachments. Files are uploaded unencrypted and stored under a random name. In a DM, only the message carrying the link is encrypted.
  • Group chats, Spaces channels and stories. These are stored on the server in readable form, so the server and its administrators can read them. The app labels group chats as not end-to-end encrypted.
  • Imported Skype history. It’s stored on the server as it was in your export.
  • Calls and voice channels. These open a room on the public Jitsi Meet service (meet.jit.si), whose servers carry the audio and video. Live streams and remote screen sessions use direct WebRTC connections, which are encrypted with DTLS-SRTP but may be relayed through Phaze’s TURN server.
  • Metadata. The server knows who talks to whom and when, your contact list, and the IP addresses you connect from.

Account protection

  • Passwords are stored as bcrypt hashes with a cost factor of 12.
  • Sign-up requires a verified email address, and disposable email domains are refused.
  • Signing in from a new device has to be approved from a device that’s already signed in, or with a code sent to your email.
  • Optional two-factor authentication works with any TOTP authenticator app.
  • You can list your active sessions and revoke any of them, and sign in on a new device by scanning a QR code from a trusted one.
  • Requests are rate-limited, and the admin tools sit behind a separate login that can be restricted to specific IP addresses.

Report a vulnerability

If you’ve found a security problem in Phaze, please report it privately so it can be fixed before it’s public.

Open a private security advisory on GitHub

The advisory is visible only to you and the maintainers. Please include:

  • What the problem is and what an attacker could do with it.
  • Steps to reproduce it, or a proof of concept.
  • Which part is affected: the server, the web app, the Android app or the desktop app, and the version if you know it.

Please don’t open a public issue for security bugs. When testing, use your own accounts: don’t access other people’s data, don’t degrade the service for others, and stop once you’ve shown the problem exists. Phaze is a small independent project and doesn’t run a paid bug bounty, but valid reports can be credited in the advisory if you’d like.
